1. Roles and access control

Every account has one role. The role is stored with the account and read at sign-in.

RoleWhoHow the account is created
CUSTOMERStore customersSelf sign-up on the Sign In page, or the sample data
ADMINStore administratorsSample data only (user admin). There is no screen to create an administrator.

Protected pages are listed in WEB-INF/signon-config.xml. A page with an auth-constraint is open only to the roles listed; a page without one is open to any signed-in user. When an anonymous user opens a protected page, the Sign In page is shown and, after a successful sign-in, the user is sent back to the page first asked for.

When signed in as ADMIN the banner shows an extra Admin link.

2. Sign-on rules

#Rule
R1A sign-in succeeds when the user exists, is not locked and the password matches exactly.
R2Each failed sign-in adds 1 to the account's failed attempts. A successful sign-in sets it back to 0.
R3The 3rd failure in a row locks the account (LOCKED = Y) and records the time of the lock.
R4A locked account cannot sign in, even with the right password. The attempt is recorded as SIGNON_LOCKED and the failed count does not change.
R5Batch job PSL_ACCT_UNLOCK runs every 15 minutes and unlocks accounts locked more than 30 minutes ago. It sets failed attempts to 0 and records ACCOUNT_UNLOCKED.
R6A sign-in with an unknown user name is recorded as SIGNON_FAIL against the name typed.
R7Every sign-in, failure, lock, sign-out and new account is written to SIGNON_AUDIT with the time and the client address.
R8Sessions time out after 15 minutes without activity.

2.1 Unlock an account at once

There is no unlock screen. To unlock before the batch job runs, ask operations to run PSL_ACCT_UNLOCK on demand (it only unlocks locks older than 30 minutes) or to run this SQL as the store schema owner:

UPDATE signon SET locked = 'N', failed_attempts = 0, locked_ts = NULL WHERE username = '<user>';
INSERT INTO signon_audit (username, event_type, event_ts, remote_addr)
  VALUES ('<user>', 'ACCOUNT_UNLOCKED', CURRENT_TIMESTAMP, 'admin');

3. Catalog administration

The catalog and the sample accounts come from two files in the web application:

FileContent
populate/Populate-UTF8.xmlUsers (id, password, role) and the catalog: 5 categories, 16 products, 28 items
populate/PopulateSQL.xmlCreate, insert, check and drop statements per table, for derby and oracle

3.1 First load

When a user clicks enter the store, the store calls Populate?forcefully=false. If the catalog and SIGNON tables already hold data nothing happens. Otherwise every table is dropped, created and loaded. No sign-in is needed for the first load.

3.2 Reload the sample data

  1. Sign in as an ADMIN user.
  2. Click Admin in the banner. The page Catalog Administration opens.
  3. Click Reload Sample Data.
  4. The store drops and recreates CATEGORY, CATEGORY_DETAILS, PRODUCT, PRODUCT_DETAILS, ITEM, ITEM_DETAILS, SIGNON and SIGNON_AUDIT, loads the file, ends your session and shows the home page.
A reload deletes every account created in the store and all sign-in history. Take a backup first (job PSL_DB_BACKUP).

3.3 Catalog data rules

#Rule
C1Every category has at least one product.
C2Every product has at least one item.
C3An item's list price is never below its unit cost (database check constraint).
C4Every item has an en_US description.

Job PSL_CATALOG_CHECK checks C1 to C4 every morning at 06:00 and alerts the catalog team when one fails.
